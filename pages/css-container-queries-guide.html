A Practical Guide to CSS Container Queries

Media queries ask about the viewport. Container queries ask about the component. Here's how to actually use that difference in production layouts.

Daniel Reyes
Senior Infrastructure Engineer

For as long as responsive design has existed, it has meant one thing in practice: media queries that check the viewport width and adjust layout accordingly. That works fine when a component only ever appears in one context. It breaks down the moment the same card, the same sidebar widget, the same navigation item needs to look different depending on how much space its parent happens to give it — a sidebar on a wide screen, a full-width column on a narrow one, sometimes both on the same page.

Container queries fix this by asking a more useful question: not "how wide is the browser window," but "how wide is the box this component actually lives in."

Setting up a containment context

A container query only works if you tell the browser which element to measure. That means opting an ancestor into containment explicitly:

.card-wrapper {
  container-type: inline-size;
  container-name: card;
}

container-type: inline-size tells the browser to track the element's width (the common case) and establish size containment, which also has a performance benefit — the browser can lay out that subtree somewhat independently. The container-name is optional but worth adding once you have more than one container type on a page, so your queries can target the right one.

Writing the query itself

Once a container is declared, any descendant can query against it using @container instead of @media:

@container card (min-width: 400px) {
  .card {
    grid-template-columns: 120px 1fr;
  }
}

The rule inside only applies when the nearest ancestor container named "card" is at least 400px wide — regardless of whether the browser window is 320px or 3200px. Drop that same card into a narrow sidebar and a wide main column on the same page, and each instance responds to its own available space independently.

Media queries describe the page. Container queries describe the component. Most real layout problems are actually the second kind — we just didn't have a tool for it until recently.

Container query units: the other half of the feature

Alongside @container rules, CSS added units that resolve relative to the nearest container instead of the viewport: cqw, cqh, cqi, cqb, and cqmin/cqmax for the smaller or larger of the two axes. This lets you size type or spacing proportionally to a component's own box:

.card-title {
  font-size: clamp(1rem, 4cqi, 1.5rem);
}

That heading now scales with the width of its own container, not the page — useful for components designed to be genuinely reusable across very different layout contexts.

A common gotcha

You can't query a container's size from an element that is itself establishing that same containment context — a container can't query itself. In practice this just means the containment declaration goes one level up from where you write your @container rules: contain on the wrapper, query from the children.

Where to actually use this

  • Card components that appear in both grids and sidebars
  • Dashboard widgets that get resized or dragged into differently sized panels
  • Design system components meant to be dropped into arbitrary contexts by other teams

You don't need to replace every media query with a container query — page-level layout decisions, like switching a whole page from a single column to a multi-column grid, are still exactly what media queries are for. The rule of thumb is simple: if the question is about the page, use a media query; if the question is about the box a component actually lives in, reach for a container query instead.
